#S1|Harbor Outfitters is building a support resolution agent on the Claude Agent SDK. It has custom MCP tools `get_customer`, `lookup_order`, `process_refund` and `escalate_to_human`. The target is 80%+ first-contact resolution. Human agents see only what the agent sends them. Company policy allows the agent to refund up to $300.

@1.1|S1|M
During testing, a developer's loop sometimes ends with the customer's order unprocessed. The loop stops whenever a response contains a text block, on the theory that text means Claude has finished. What change fixes the cause?
+ Decide on `stop_reason`, continuing on `tool_use` and stopping on `end_turn`, whether or not text is present
- Add a system prompt rule that Claude must never write any text in a response that also calls a tool
- Keep the text check, and add a regular expression that looks for phrases such as "let me check" before stopping
- Stop only after a fixed number of iterations, chosen to be larger than the longest conversation in the logs
= A response can carry text alongside a tool call, so text doesn't mean completion. `stop_reason` is the explicit signal. The prompt rule and the regex keep a fragile signal, and a fixed count is the guide's named anti-pattern when used as the main stop.

@1.1|S1|H
Which design best fits this agent's mix of predictable and unpredictable requests?
+ Let Claude choose the next tool from what it has learned so far, with code enforcing the few rules that must always hold
- Encode every return, billing and account path as a decision tree, and have Claude only write the wording of the replies
- Fix one sequence of get_customer, lookup_order and process_refund, and run it for every incoming message
- Let Claude choose all tools, and rely on an instruction asking it to follow the refund policy carefully
= High-ambiguity requests suit model-driven decisions, while guarantees belong in code. A decision tree or a fixed sequence can't adapt, and an instruction alone is probabilistic.

@1.4|S1|M
In 3% of logged cases, `process_refund` ran before identity had been verified, despite a clear instruction in the system prompt. Which change gives a deterministic guarantee?
+ Block `process_refund` in code until `get_customer` has returned a verified customer ID in this session
- Move the instruction to the top of the system prompt and repeat it in capital letters at the end as well
- Add several few-shot examples that show verification happening before each refund is issued
- Add a review step in which Claude confirms in text that it has verified identity before refunding
= Any prompt technique leaves a non-zero failure rate. A programmatic prerequisite makes the wrong order impossible. A text confirmation is still model output, and not a check.

@1.4|S1|M
A customer's message reads: "My jacket arrived torn, you charged me twice for it, and I've moved house." What should the agent do?
+ Treat these as three concerns, investigate them in parallel with shared context, and give one unified reply
- Resolve the torn jacket first, because it appears first, then ask the customer to send the other issues again
- Escalate to a human, because any message with more than one concern is too complex for an agent to handle
- Open three separate sessions so that each concern has a clean context, and send three separate replies
= The guide's pattern is decompose, investigate using shared context, then synthesize. Handling only the first drops work, multi-concern isn't an escalation trigger, and separate sessions lose shared facts.

@1.4|S1|H

+ A structured summary with customer ID, root cause, refund amount and recommended action

- A one-line note saying that the customer needs help with a refund and that a human should take over
